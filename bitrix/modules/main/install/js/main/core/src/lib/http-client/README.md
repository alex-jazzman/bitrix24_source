# HttpClient

Современная клиентская HTTP-библиотека ядра: единый типизированный класс
`HttpClient` — транспорт на `fetch` (сырые методы `request`/`get`/`post`/…) и
вызовы Engine-контроллеров (`action`/`actionRaw`). Замена `BX.ajax` для нового
кода. Legacy `BX.ajax` не затрагивается и продолжает работать.

Канонический способ потребления — импорт из ядра:

```js
import { HttpClient } from 'main.core';
```

Глобально контракт доступен как `BX.HttpClient` — сборщик раскладывает
именованные экспорты `main.core` в `BX`. Классы ошибок и хелперы конверта
объявлены статикой самого клиента, поэтому вся библиотека достаётся одним
именем:

```js
const { HttpClient } = BX;

try
{
    await BX.HttpClient.action('some.action');
}
catch (error)
{
    if (error instanceof BX.HttpClient.ControllerError)
    {
        showErrors(error.errors);
    }
}
```

Классы ошибок дополнительно лежат в корне (`BX.ControllerError` и остальные) —
тем же побочным эффектом сборки. Предпочитайте форму `BX.HttpClient.*`: она
не зависит от того, какие имена ядро разложит в `BX`.

Не путайте с legacy `BX.Http` — там живут `Cookie` и `Data`, к этой библиотеке
они отношения не имеют.

## Статика и инстансы

Статические методы работают через ленивый дефолтный инстанс, преднастроенный на
текущий портал (создаётся при первом обращении, один на страницу) — удобно для
разовых вызовов:

```js
import { HttpClient } from 'main.core';

const items = await HttpClient.action('crm.item.list', {
	data: { entityTypeId: 2 },
});

const { data } = await HttpClient.get('/some/raw/endpoint.php');
```

Свой инстанс — когда нужна изоляция или базовая конфигурация. Инстансы независимы
от дефолтного, их interceptors не наследуются:

```js
const client = new HttpClient({
	baseUrl: '/some/api/',
	timeout: 5000,
	headers: { 'X-Custom': 'value' },
});
```

Поля `ClientConfig`:

| Поле | Назначение |
|---|---|
| `baseUrl` | база для относительных URL **сырых** методов (`request`/`get`/`post`/…). **Не влияет на `action`/`actionRaw`** — action-путь всегда строит URL от `controllerEndpoint`. |
| `controllerEndpoint` | endpoint Engine-контроллеров для `action`/`actionRaw`, по умолчанию `/bitrix/services/main/ajax.php`. Резолвится относительно текущей страницы; `baseUrl` игнорируется. |
| `headers` | заголовки по умолчанию для всех запросов инстанса. |
| `timeout` | таймаут в мс (`0` — без таймаута). |
| `query` | query-параметры по умолчанию. |
| `retry` | политика повторных попыток для всех запросов инстанса, по умолчанию повторов нет — см. «Повторные попытки». |

## Вызов action контроллера

`action`/`actionRaw` обращаются к Engine-контроллеру (`controllerEndpoint`, по
умолчанию `/bitrix/services/main/ajax.php`): CSRF-токен и `X-Bitrix-Site-Id` на
same-origin запросах, один тихий повтор при `invalid_csrf`, конвейер ассетов
(`X-Process-Assets`). URL action строится от `controllerEndpoint` и игнорирует
`baseUrl`.

Результат action ядро отдаёт не напрямую, а внутри стандартного ответа
контроллера:

```json
{
	"status": "success",
	"data": { "items": [] },
	"errors": []
}
```

Полезная нагрузка лежит в `data`, `status` принимает значения `success`, `error`
или `denied` (не хватило прав), в `errors` — список ошибок контроллера.
`action()` отдаёт содержимое `data` и превращает неуспешный ответ в
`ControllerError`; `actionRaw()` возвращает всю структуру целиком (в коде она
называется `AjaxEnvelope`). Такой ответ отдают не все типы — см. «Типы ответов
контроллера».

```js
import { HttpClient } from 'main.core';

// резолвится полем `data`
const items = await HttpClient.action('crm.item.list', {
	data: { entityTypeId: 2 },
});

// для action без данных это `null`: saveOptions ничего не возвращает
const nothing = await HttpClient.action('main.userOption.saveOptions', {
	data: { newValues: { ui: { theme: 'dark' } } },
});

// вся структура {status, data, errors}
const envelope = await HttpClient.actionRaw('crm.item.list', {
	data: { entityTypeId: 2 },
});
```

Опции action (`ActionOptions`): `data` (объект или `FormData`), `json`, `query`,
`navigation: {page, size}`, `analytics`/`analyticsLabel`, `method` (по умолчанию
`POST`), `headers`, `timeout` (мс), `signal`, `retry` (см. «Повторные попытки»).

`ActionOptions` — объединение двух вариантов: с телом (`method` — `POST`, `PUT`,
`PATCH` или `DELETE`, доступны `data` и `json`) и без тела (`method: 'GET'` либо
`'HEAD'`, `data`/`json` запрещены — полезную нагрузку кладите в `query`).
Запрос без тела с `data` не компилируется, а не падает в рантайме.

`analytics` и `analyticsLabel` взаимоисключающие: если заданы оба, побеждает
`analytics`, а `analyticsLabel` отбрасывается с сообщением в консоли. Невалидный
`analytics` (не объект; пустые `event`/`tool`/`category`; `p1`…`p5` не строка или
больше одного подчёркивания) тоже отбрасывается — ошибка пишется в консоль, но
сам запрос не блокируется и уходит без аналитических параметров.

## Типы ответов контроллера

`action()`/`actionRaw()` работают со стандартным ответом `{status, data, errors}`,
а его отдают не все типы. Правило одно и проверяется по коду action
(`HttpApplication::buildResponse`): **если action вернул объект `HttpResponse` —
он уходит клиенту как есть; всё остальное (массив, объект, `null`) ядро
упаковывает в стандартный ответ.**

| Что возвращает action | Стандартный ответ | Чем брать с фронта |
|---|---|---|
| массив, объект, `null` | да | `action()` |
| `Response\AjaxJson` | да | `action()` |
| `Response\HtmlContent` | да | `action()` → `data.html` |
| `Response\Component` | да | `action()` → `data.html` |
| `Response\Json` | **нет** | сырой транспорт |
| `Response\File`, `BFile`, `ResizedImage` | **нет** | ссылка или `responseType: 'blob'` |
| `Response\Zip\Archive` | **нет** | ссылка или `responseType: 'blob'` |
| `Response\Redirect` | **нет** | см. ниже — на action-пути реджектится |

Вызов `action()` на сыром ответе реджектится `ParseError`: клиент получил 2xx, но
структуры `{status, data, errors}` в теле не нашёл.

### Результат работы компонента

`HtmlContent` и `Component` отдают стандартный ответ, просто в `data` лежит
`{html, assets, additionalParams}`. Оба типа сами ставят заголовок
`X-Process-Assets`, поэтому css/js/настройки из `data.assets` загружаются **до
того, как зарезолвится промис**: к моменту вставки HTML зависимости уже на месте.
Конвейер координируется с legacy `BX.load`, так что файл не будет скачан дважды.

```js
const { html } = await HttpClient.action('bizproc.fieldtype.renderControl', {
	data: { documentType, property, params },
});

BX.Runtime.html(node, html);
```

Что именно лежит в `html`, задаёт контроллер: переданный в `HtmlContent` объект
`ContentAreaInterface` может отдать как строку, так и массив кусков (например,
`bizproc.fieldtype.renderControlCollection` возвращает массив по одному элементу
на контрол). Смотрите на свой контроллер, а не на форму из примера.

Если action объявлен как `?Component` и при ошибке делает `addError()` +
`return null`, ответ остаётся стандартным, но со `status: 'error'` — на клиенте
это обычный `ControllerError` с заполненным `errors`.

Упаковывать компонент вручную в голый `HttpResponse` ради сырого HTML не нужно:
`action()` + `data.html` даёт тот же результат и вдобавок грузит ассеты.

### Сырые ответы

Для них нужен сырой транспорт — он ничего не ждёт от тела и отдаёт его как есть:

```js
// Response\Json и любой не-Engine эндпоинт
const { data } = await HttpClient.get('/some/raw/endpoint.php');

// файл или архив, когда содержимое нужно в JS
const { data: blob } = await HttpClient.get('/path/to/file', { responseType: 'blob' });
```

Файл, который нужно просто отдать пользователю, забирать через ajax не стоит —
проще обычная ссылка на скачивание.

**`Redirect` на action-пути не сработает намеренно.** Action-запросы выполняются
с `redirect: 'error'`, поэтому ответ 302 реджектится `NetworkError` вместо
перехода. Так портальные заголовки не уезжают на адрес редиректа (см.
«Безопасность»). Такой контроллер вызывайте сырым транспортом или переходите по
ссылке обычной навигацией.

## Произвольные HTTP-запросы

```js
import { HttpClient } from 'main.core';

const client = new HttpClient({ baseUrl: '/some/api/', timeout: 5000 });

const { data, status, headers } = await client.get('items', { query: { page: 2 } });
await client.post('items', { title: 'New item' }); // объект уходит как x-www-form-urlencoded
await client.put('items/1', null, { json: { title: 'JSON body' } });
```

Методы: `request(config)`, `get/delete/head(url, config?)`,
`post/put/patch(url, body?, config?)`. Ответ (`HttpResponse`):
`{ status, ok, headers, data, raw, retryCount }`; `data` разобрана согласно
`responseType` (`json` по умолчанию, также `text` | `blob` | `formData`),
а `raw` пригодна только для метаданных — см. ниже.
Тип поля — `T | null`: пустое 2xx-тело в `json`-режиме даёт `null`, поэтому
перед обращением к полям проверяйте значение:

```js
const { data } = await client.get('items/1');
if (data !== null)
{
	console.log(data.title);
}
```

Поле `raw` — нативный `Response` **только ради метаданных** (`url`, `redirected`,
`type`, `status`). Его тело уже вычитано при разборе ответа и лежит в `data`,
поэтому `response.raw.json()`/`.text()` бросят «body stream already read».

Поле `retryCount` — сколько повторов потрачено до этого ответа; у ответа с первой
попытки это `0`, проверять наличие поля не нужно. Подробнее — «Сколько повторов
было».

`get/delete/head` не принимают `body`/`json`; `GET`/`HEAD`-запрос с телом
реджектится понятным `TypeError` ещё до отправки.

## Interceptors

У каждого инстанса — одна пара цепочек `request`/`response` (транспортный
уровень); они видят и сырые запросы, и action-запросы. Request-обработчик
получает эффективную конфигурацию запроса: дефолты инстанса (`baseUrl`, `query`,
`timeout`, …) уже слиты с конфигом вызова, а заголовки обоих уровней собраны в
один экземпляр `Headers` — обработчик видит запрос таким, каким он будет
отправлен, и может убрать в том числе дефолтный заголовок инстанса и выведенный
из тела `Content-Type` (заменив тело на другой тип полезной нагрузки, обработчик
отвечает и за соответствующий `Content-Type`). Поле `headers` эффективной
конфигурации — всегда готовый экземпляр `Headers`. Семантика
как у axios: обработчик может заменить значение, вернув новый объект (не мутируя
полученный), `onRejected` — восстановиться после ошибки.

> **Статические interceptors — общие на всю страницу.** `HttpClient.interceptors`
> живут на дефолтном инстансе, через который идут все статические вызовы продукта.
> Первый же модуль, повесивший туда логирование, редирект на 401 или подмену
> заголовков, изменит поведение чужих статических вызовов во всех модулях
> страницы. Для своей логики заводите собственный инстанс (`new HttpClient()`) —
> его interceptors изолированы и на статические вызовы не влияют, как и
> статические на него.

```js
const id = client.interceptors.request.use((config) => {
	// копия ради иммутабельности: общий Headers из конфига мутировать нельзя
	const headers = new Headers(config.headers);
	headers.set('X-Trace-Id', generateId());

	return { ...config, headers };
});

client.interceptors.response.use(
	(response) => response,
	(error) => {
		console.error(error);
		throw error;
	},
);

client.interceptors.request.eject(id);
```

## Межвкладочная блокировка

Когда портал открыт в нескольких вкладках и все они реагируют на одно событие,
каждая вкладка шлёт серверу один и тот же запрос. Опция `crossTabLockKey`
выстраивает такие вызовы в очередь: вкладки с одинаковым ключом договариваются на
блокировке уровня источника (`navigator.locks`), одна из них идёт в сеть, а
остальные ждут и разрешают свой вызов её результатом, не отправляя своего
запроса. Ключ — свойство вызова, а не инстанса: вкладки находят друг друга по
имени ключа, а не по объекту клиента и не по адресу.

```js
// во всех вкладках портала это один запрос на сервер вместо N
const { data } = await HttpClient.action('some.controller.counters', {
	crossTabLockKey: 'im.counters',
	crossTabLockTimeout: 5000, // страховка от подвисания; по умолчанию — значение timeout
});
```

### Когда это нужно

Блокировка решает одну задачу: **несколько вкладок одновременно узнают об одном и
том же и одновременно идут за одними и теми же данными**. Признак такой ситуации —
запрос порождается не действием пользователя, а внешним сигналом, который приходит
во все открытые вкладки сразу.

Типичные случаи:

- **Реакция на событие пула.** Пул доставляет событие в каждую вкладку, и каждая
  идёт обновлять счётчики, список чатов, состояние документа. Это исходный сценарий
  из тикета 0170574.
- **Обновление по таймеру,** заведённому в каждой вкладке: раз в минуту все они
  просыпаются почти одновременно.
- **Реакция на возврат фокуса или выход из спящего режима,** когда браузер будит
  сразу все вкладки портала.
- **Общий для вкладок ресурс, который дорого считать на сервере** — тяжёлая сводка,
  пересчёт прав, выгрузка настроек.

Полный пример — сценарий из тикета, переписанный на новый транспорт:

```js
BX.PULL.subscribe({
	moduleId: 'im',
	command: 'counterUpdate',
	callback: async () => {
		// событие придёт во все вкладки, но на сервер уйдёт один запрос
		const { data } = await HttpClient.action('im.counters.get', {
			crossTabLockKey: 'im.counters.get',
			crossTabLockTimeout: 5000,
		});

## Повторные попытки

Единичный сбой связи — оборванное соединение, 503 от балансировщика, таймаут на
медленном канале — по умолчанию сразу превращается в ошибку. Политика `retry`
включает встроенный цикл повторов: библиотека сама повторит попытку, выждав
паузу, и отдаст ошибку только когда повторять больше нечем или незачем.

**По умолчанию механизм выключен** (`retries: 0`) — вызов без явной настройки
ведёт себя ровно так же, как до появления повторов.

```js
// политика на инстансе — действует на все его запросы
const client = new HttpClient({
	baseUrl: '/some/api/',
	retry: { retries: 2 },
});

const { data } = await client.get('items'); // GET: при 503 повторится до двух раз

// политика на вызове сливается с политикой инстанса по полям: здесь у запроса
// будет retries: 3 и delay: 500, остальные значения — от инстанса
await client.get('items', { retry: { retries: 3, delay: 500 } });

// повторы для одного сырого запроса, без настройки инстанса
await HttpClient.get('/some/raw/endpoint.php', { retry: { retries: 1 } });
```

### Что повторяется

Повтор происходит, только когда выполнены **оба** условия.

**Бюджет попыток.** `retries` больше нуля. Значение — число повторов *сверх*
первой попытки: `retries: 2` означает не больше трёх попыток. На action-пути к
ним может добавиться одна тихая переотправка со свежим CSRF-токеном — она бюджет
не расходует, см. «Ограничения».

**Безопасность повтора.** Метод не должен менять состояние на сервере. Сама
собой повторяется только тройка `GET`, `HEAD`, `OPTIONS`. Любой другой метод
повторяется, лишь когда вызывающий код объявил вызов безопасным опцией
`idempotent: true`.

Ошибка попытки должна оказаться пригодной к повтору. Встроенный классификатор:

| Ошибка | Повторяется по умолчанию |
|---|---|
| `NetworkError` | да — ответ не получен вовсе |
| `TimeoutError` | да — таймаут попытки |
| `HttpError` со статусом 408, 425, 429, 500, 502, 503, 504 | да — сервер объявил сбой временным |
| `HttpError` с любым другим статусом | нет |
| `ControllerError` | нет — доменный отказ, повтор ничего не изменит |
| `ParseError` | нет — тело испорчено детерминированно |
| `AssetLoadError` | нет — экшен уже выполнен успешно |
| `DOMException` с `name === 'AbortError'` | нет — отмену повторять запрещено |
| `TypeError` | нет — ошибка программиста |

### `idempotent` — утверждение о серверной семантике

`idempotent: true` — это **ваше утверждение о том, что делает экшен на сервере**:
«я проверил, этот вызов можно выполнить дважды, и второй раз ничего не испортит».
Это не настройка производительности и не «разрешение повторять на всякий случай».

Если объявить безопасным вызов, который на самом деле пишет, — **операция
выполнится дважды**: задача создастся два раза, счёт спишется два раза. Библиотека
проверить это не может: у action-пути метод почти всегда `POST`, и из имени
экшена его семантика не следует.

```js
// чтение: повторять безопасно, экшен только выбирает данные
const items = await HttpClient.action('crm.item.list', {
	data: { entityTypeId: 2 },
	retry: { retries: 2, idempotent: true },
});

// запись: idempotent НЕ ставим — при таймауте получим TimeoutError, а не вторую сделку
await HttpClient.action('crm.item.add', {
	data: { fields },
	retry: { retries: 2 },
});
```

**Опция действует только на уровне отдельного вызова** — в `RequestConfig.retry`
сырого запроса или в `ActionOptions.retry` действия. С уровня инстанса она не
наследуется: `idempotent: true` в конфиге инстанса было бы утверждением обо всех
запросах, которые через него пойдут, включая ещё не написанные, а инстанс не
знает, какие из них пишут.

Тип `ClientConfig.retry` поле не содержит, поэтому TypeScript укажет на ошибку
прямо в месте объявления. В рантайме поле отбрасывается при создании клиента, а в
консоль уходит сообщение, что настройка проигнорирована:

```js
// так — нет: поле отбрасывается, POST этого инстанса остаётся неповторяемым
const client = new HttpClient({ retry: { retries: 2, idempotent: true } });
await client.action('crm.item.list'); // при 503 — ControllerError, повтора нет

// так — да: бюджет от инстанса, утверждение о семантике — от вызова
const client = new HttpClient({ retry: { retries: 2 } });
await client.action('crm.item.list', { retry: { idempotent: true } }); // повторится
```

Остальные поля политики (`retries`, `delay`, `maxDelay`, `respectRetryAfter`,
`totalTimeout`, `shouldRetry`, `calculateDelay`, `onRetry`) наследуются от
инстанса как обычно.

### Поля `RetryConfig`

| Поле | Тип | Умолчание | Назначение |
|---|---|---|---|
| `retries` | `number` | `0` | максимальное число **повторов** сверх первой попытки; `0` выключает механизм |
| `idempotent` | `boolean` | `false` | вызывающий код утверждает, что запрос безопасно выполнить дважды; разрешает повтор для метода вне тройки `GET`/`HEAD`/`OPTIONS`. **Только на уровне вызова** — с инстанса не наследуется |
| `delay` | `number` | `300` | базовая пауза в мс, от которой считается экспонента |
| `maxDelay` | `number` | `10000` | потолок одной паузы в мс; ограничивает и экспоненту, и `Retry-After` |
| `respectRetryAfter` | `boolean` | `true` | учитывать заголовок `Retry-After` ответа |
| `totalTimeout` | `number` | `0` | общий бюджет операции в мс со всеми паузами; `0` — без бюджета |
| `shouldRetry` | `(context: RetryContext) => boolean` | встроенный классификатор | собственный предикат пригодности ошибки |
| `calculateDelay` | `(context: RetryContext) => number` | встроенный расчёт | собственная функция расчёта паузы в мс |
| `onRetry` | `(context: RetryContext & { delay: number }) => void` | — | наблюдательный колбэк перед каждым повтором |

Числовые поля нормализуются: значение неверного типа, `NaN` и бесконечность
откатываются к умолчанию, конечное значение вне диапазона зажимается — паузы и
бюджет времени снизу нулём, `retries` — в `[0, 100]`. Осмысленные нули
(`retries: 0`, `delay: 0`, `totalTimeout: 0`) при этом сохраняются. Смысл в том,
что опечатка в знаке дала бы отрицательную паузу, которую `setTimeout` читает как
ноль, — повторы пошли бы вплотную, без того самого разброса; а `retries: Infinity`
дал бы серию, которую нечем остановить.

Политика объявляется на трёх уровнях: `ClientConfig.retry` (инстанс),
`RequestConfig.retry` (сырой вызов) и `ActionOptions.retry` (вызов action).
Слияние — обычное для конфигов библиотеки и **пополевое**: вызов переопределяет
только те поля политики, которые сам назвал, остальные достаются от инстанса.
Целиком заменить политику инстанса на уровне вызова нельзя — можно перечислить
нужные поля явно. Единственное исключение из наследования — `idempotent`: уровень
инстанса его не принимает, см. раздел выше.

### Паузы между попытками

Верхняя граница паузы растёт экспоненциально от `delay` — `delay * 2 ** retryCount`
— и упирается в `maxDelay`. Сама пауза выбирается случайно в диапазоне от нуля до
этой границы (full jitter), поэтому при `delay: 300` первый повтор ждёт от 0 до
300 мс, второй — от 0 до 600 мс и так далее. Разброс не отключается: без него
сотни вкладок, разом получивших 503 от перезапущенного балансировщика, повторят
синхронно и добьют бэкенд. Нужна детерминированная пауза — задайте
`calculateDelay`.

Если ответ несёт `Retry-After` (в секундах или в форме HTTP-даты) и
`respectRetryAfter` не выключен, используется указание сервера — тоже
ограниченное `maxDelay`: сервер вправе просить подождать, но не вправе занять
вкладку на час.

Пауза прерывается отменой: `controller.abort()` во время ожидания реджектит вызов
нативным `AbortError` немедленно, следующей попытки не будет.

### Поля `RetryContext`

Контекст получают `shouldRetry`, `calculateDelay` и `onRetry`.

| Поле | Тип | Назначение |
|---|---|---|
| `error` | `unknown` | ошибка завершившейся попытки — уже в виде класса библиотеки |
| `attempt` | `number` | номер завершившейся попытки, с 1 |
| `retryCount` | `number` | сколько повторов уже выполнено (`attempt - 1`) |
| `method` | `HttpMethod` | метод запроса в верхнем регистре |
| `config` | `EffectiveRequestConfig` | эффективный конфиг попытки |
| `policy` | `NormalizedRetryPolicy` | политика с подставленными умолчаниями |

> **Не логируйте контекст целиком.** В `config.headers` лежат портальные
> заголовки запроса, включая действующий CSRF-токен портала. `onRetry` — точка
> для логов и метрик, поэтому соблазн отправить туда весь контекст велик: берите
> из него нужные поля (`attempt`, `retryCount`, `delay`, `error`), как в примере
> ниже, а не объект целиком.

```js
// свой предикат: заменяет встроенный классификатор целиком
await client.get('items', {
	retry: {
		retries: 2,
		shouldRetry: ({ error }) => error instanceof HttpError && error.status === 503,
	},
});

// свой расчёт задержки: фиксированная пауза вместо экспоненты
await client.get('items', {
	retry: {
		retries: 3,
		calculateDelay: () => 1000,
	},
});

// наблюдение: логирование и метрики, на решение не влияет
await client.get('items', {
	retry: {
		retries: 2,
		onRetry: ({ attempt, delay, error }) => {
			console.warn(`попытка ${attempt} не удалась, повтор через ${delay} мс`, error);
		},
	},
});
```

### Когда не нужно

- **Запрос от действия пользователя.** Нажатие кнопки происходит в одной вкладке,
  конкуренции нет — ключ добавит ожидание очереди и ничего не сэкономит.
- **Вкладки запрашивают разные данные.** Ключ координирует по имени, а не по адресу
  и не по телу запроса: вкладки с одним ключом обменяются снимками ответов на разные
  запросы. Если параметры вызова различаются, они должны попасть в ключ
  (`im.chat.history:${chatId}`) или блокировка не нужна вовсе.
- **Ответ зависит от состояния конкретной вкладки** — тогда чужой результат ей не
  подходит по смыслу.
- **Запрос и так редкий.** Экономия проявляется только в окне конкуренции; вызов,
  пришедший после того, как ведущая вкладка завершилась, выполняется сам по себе.
- **Нужен кеш, а не очередь.** Механизм ничего не хранит — см. ниже.

- **Нужен защищённый контекст.** `navigator.locks` доступен только по https (а
  также в Safari от 15.4 и Firefox от 96). Без него ключ молча игнорируется:
  вызов уходит в сеть как обычный, без ошибки и без записи в журнал.
- **Ждущая вкладка получает снимок ответа**, а не живой ответ: статус, признак
  успешности, отобранный набор заголовков и разобранное тело. Итоговый адрес
  между вкладками не переносится: у восстановленного ответа `raw.url` пуст, потому
  что адрес ответа управляет повтором при смене CSRF-токена и загрузкой ассетов —
  решениями, которые нельзя основывать на содержимом сообщения.
  Ошибка ведущей вкладки доставляется тем же каналом и пересобирается в
  эквивалентную типизированную ошибку, так что `instanceof` работает одинаково в
  обеих вкладках. Перехватчики ответа отрабатывают у каждой вкладки своей
  цепочкой — поверх настоящего ответа у ведущей и поверх восстановленного у
  ждущей.
- **Ограничение по типу ответа.** `responseType: 'formData'` между вкладками не
  переносится, и такой запрос выполняется каждой вкладкой самостоятельно, как
  если бы ключа не было. Переносятся `json`, `text` и `blob`.
- **Не ставьте ключ на действия, возвращающие ассеты.** Если ответ помечен
  заголовком `X-Process-Assets`, ведущая вкладка ассеты загрузит, а ждущие — нет:
  их вызов разрешится телом ответа, но стили, сценарии и строки настроек у них не
  применятся. Это следствие того, что адрес ответа между вкладками не переносится.
- **Только очередь, никакого кеша.** Результат раздаётся ждущим в границах одного
  окна конкуренции. Вызов, пришедший после того, как ведущая вкладка уже
  завершилась, открывает новое окно и выполняет собственный запрос. Кому нужен
  кеш — ставит его поверх, перехватчиком ответа или собственным хранилищем.
- **Пропажа ведущей вкладки не подвешивает остальных.** Браузер снимает
  блокировку при закрытии вкладки, и одна из ждущих становится ведущей сама.
  `crossTabLockTimeout` — последний рубеж на случай, когда не пришли ни
  сообщение, ни блокировка: по его истечении вызов отклоняется `TimeoutError`.
  По умолчанию он равен `timeout`, и эти два бюджета идут подряд, а не общим
  счётом: таймаут запроса взводится уже после захвата блокировки, поэтому вкладка
  может прождать очередь и получить на сеть полный срок заново. Нужен потолок на
  весь вызов — задавайте `crossTabLockTimeout` явно.
- **Тело ответа становится видимым всем контекстам источника.** Канал вкладок
  общий для всего источника, поэтому снимок читает и сторонний код на странице —
  приложение маркетплейса во вложенном окне, виджет. Не ставьте ключ на вызовы,
  возвращающие секреты, токены или персональные данные, доступные не всякому
  скрипту страницы. Сообщения из канала проверяются по строгому контракту, а
  заголовки восстанавливаются только из фиксированного набора имён, но само тело
  ответа фильтрации не подлежит — за него отвечает вызывающая сторона.
- **Ключи именуйте с пространством имён** — `im.counters`, а не `counters`. Имя
  ключа служит и именем канала, и именем блокировки: два независимых модуля,
  выбравшие одну строку, попадут в одну очередь и обменяются снимками ответов на
  разные запросы.
- **Опция рассчитана на короткие служебные ответы.** Под блокировкой выполняются
  и подготовка запроса, и разбор тела, поэтому на крупных ответах разбор станет
  заметной частью удержания очереди.

Без `crossTabLockKey` поведение не меняется: ни блокировка, ни канал рассылки не
создаются.
`onRetry` действительно на решение не влияет: его исключение перехватывается,
сообщается в `console.error` и серию не обрывает — упавший логгер не подменит
ошибку сервера своей. У `shouldRetry` и `calculateDelay` такой защиты нет: они
участвуют в решении, и их исключение уходит вызывающему коду.

Собственный `shouldRetry` может только **сузить** множество повторяемых исходов
относительно инвариантов слоя, но не расширить его: отмена вызывающей стороной,
исчерпанный бюджет попыток, небезопасный метод и непереиспользуемое тело
проверяются до предиката, и вернуть на них `true` невозможно.

### Сколько повторов было

Число выполненных повторов лежит в поле `retryCount` — и у любой ошибки
библиотеки, и у успешного `HttpResponse`. У исхода, полученного без повторов, это
`0`: проверять наличие поля не нужно ни на одном из путей.

```js
try
{
	await client.get('items');
}
catch (error)
{
	if (error instanceof HttpClientError && error.retryCount > 0)
	{
		console.warn(`не удалось после ${error.retryCount} повторов`);
	}
}
```

```js
const response = await client.get('items', { retry: { retries: 2 } });
if (response.retryCount > 0)
{
	console.info(`успех достался ${response.retryCount}-м повтором`);
}
```

Нативные `AbortError` и `TypeError` счётчика не несут: они принадлежат не
библиотеке, и она их не трогает.

Счётчик считает всю операцию, а не последнюю отправку. Это заметно на
action-пути: `ControllerError`, `ParseError` и `AssetLoadError` рождаются уже
после того, как транспортная серия завершилась успехом, и всё равно сообщают
число выполненных повторов. Если за повторами последовала csrf-переотправка,
счётчик суммирует повторы обеих отправок — переотправка продолжает серию, а не
начинает свою.

### Ограничения

- **`timeout` — лимит одной попытки, а не всей серии.** Это сохранённая
  семантика: смена смысла поля молча изменила бы поведение всех существующих
  вызовов. Значит, вызов с `timeout: 3000` и `retries: 2` может суммарно занять
  заметно больше трёх секунд — три попытки плюс паузы между ними. Ограничить
  всю серию можно `totalTimeout`: перед каждой паузой проверяется, укладывается
  ли она в остаток бюджета, и если нет — повторы прекращаются и отдаётся
  последняя ошибка. Уже начатую попытку бюджет не прерывает: её обрывает
  `timeout` или отмена, а `totalTimeout` решает только, будет ли следующая.
- **Аналитика повторённого action считается дважды.** `analytics` и
  `analyticsLabel` уходят на сервер с каждой попыткой; транспортный уровень не
  знает семантики события и подавить его не вправе. Отчёты по повторённым
  вызовам завышают показатели.
- **`FormData` передаётся по ссылке.** Тело сериализуется заново на каждой
  попытке из того же значения конфига, снимок не делается. Если между попытками
  изменить объект `FormData`, повтор отправит его текущее состояние, а не то,
  что ушло первой попыткой. Копировать тело каждого запроса ради редкого случая
  пришлось бы за счёт всех запросов продукта — поэтому ограничение оставлено
  явным.
- **Тело-поток не повторяется никогда.** Запрос с `ReadableStream` в теле не
  повторяется ни при какой политике: поток вычитан первой попыткой, и повтор
  отправил бы пустое тело.
- **Interceptors видят серию один раз.** Request-цепочка отрабатывает до первой
  попытки и на повторах не прогоняется — иначе побочные эффекты чужих
  обработчиков срабатывали бы по нескольку раз. Response-цепочка получает только
  финальный исход: успех или последнюю ошибку.
- **CSRF-переотправка бюджет не удваивает.** Тихая переотправка при
  `invalid_csrf` выполняется отдельным запросом, и без согласования сценарий
  «`invalid_csrf` внутри повторяемого статуса» перемножил бы бюджеты: до
  `2 * (retries + 1)` обращений к сети. Инвариант «попытка вместе с её
  csrf-переотправкой стоит одну единицу бюджета» обеспечен переносом состояния
  серии: переотправка со свежим токеном продолжает её с уже потраченного числа
  повторов и с момента старта исходной отправки, а не открывает свои бюджеты —
  ни попыток, ни времени. Это верно на обоих путях: и когда отправка упала
  ошибкой слоя (счётчик приходит из `error.retryCount`), и когда она вернула
  конверт `invalid_csrf` по HTTP 200 (счётчик приходит из `response.retryCount`).
  Верхняя граница обращений к сети — `retries + 2`: сам бюджет плюс одна
  переотправка с новым токеном, которая по контракту выполняется не более одного
  раза.

## Обработка ошибок

Ошибки самого запроса — классы с полем `cause` и контекстом, наследующие общий
базовый класс `HttpClientError` (тоже экспортируется): `error instanceof
HttpClientError` ловит любую из них. Полный список — в таблице ниже.

От базового класса каждая ошибка наследует ещё и `retryCount` — число повторов,
потраченных запросом до этого отказа (`0`, если повторов не было). Подробности —
в разделе «Повторные попытки».

Два случая намеренно остаются вне этой иерархии:

- **отмена вызывающей стороной** (`signal` + `controller.abort()`) реджектится
  нативным `DOMException` с `name === 'AbortError'` — этого ждёт экосистема,
  включая `AbortSignal` и код, уже написанный вокруг `fetch`. Отличайте отмену
  от таймаута: таймаут клиента — это `TimeoutError` библиотеки;
- **ошибки программиста** реджектятся нативным `TypeError` — невалидное имя
  action (`HttpClient.action('badname')`) и тело в `GET`/`HEAD`-запросе. Это
  не сбой запроса, а неверный вызов: чинится в коде, а не обрабатывается в
  `catch`.

```js
try
{
	await HttpClient.action('some.controller.action', { signal });
}
catch (error)
{
	if (error instanceof DOMException && error.name === 'AbortError')
	{
		return; // вызов отменён нами же
	}

	if (error instanceof HttpClientError)
	{
		// сбой запроса: см. таблицу ниже
	}

	throw error;
}
```

Маскирование распространяется на `message` и поле `url` ошибки: значения
чувствительных query-параметров (`sessid`, `bitrix_sessid`, `csrf_token`,
токены, пароли) заменяются на `***`, как и логин с паролем в URL. Отдельно
вычищается свежий CSRF-токен из `customData.csrf` ошибки `invalid_csrf` — он не
попадает ни в `ControllerError.errors`, ни в `ControllerError.envelope`.
Остальные поля (`response`, `raw`, прочие ключи `customData`, тело ответа)
отдаются нетронутыми — это данные вашего контроллера, и при логировании ошибки
целиком за их содержимое отвечает вызывающий код.

Столбец «Ключевые поля» перечисляет поля сверх общих `cause` и `retryCount`.

| Класс | Когда | Ключевые поля |
|---|---|---|
| `HttpError` | сервер ответил не-2xx сырым телом | `status`, `response` |
| `NetworkError` | запрос не удалось отправить/получить | `url` |
| `TimeoutError` | сработал таймаут клиента | `url`, `timeout` |
| `ParseError` | тело не разобралось как `responseType` | `url`, `responseType` |
| `AssetLoadError` | не загрузился css/js-ассет из action-ответа | `url`, `assetType` |
| `ControllerError` | `status !== 'success'` либо стандартный ответ в не-2xx | `errors`, `envelope`, `httpStatus` |

```js
import { HttpClient, ControllerError, NetworkError } from 'main.core';

try
{
	await HttpClient.action('some.controller.action');
}
catch (error)
{
	if (error instanceof ControllerError)
	{
		console.error(error.errors); // [{code, message, customData?}]
	}
	else if (error instanceof NetworkError)
	{
		// сеть недоступна
	}
	else
	{
		throw error;
	}
}
```

## Безопасность

- **Портальные заголовки никогда не пересекают origin — ни прямым запросом, ни
  редиректом.** Инвариант гарантируется транспортом для любого запроса инстанса
  (и сырого, и action): `X-Bitrix-Csrf-Token`, `Bx-ajax` и `X-Bitrix-Site-Id`
  удаляются из итогового набора заголовков каждого cross-origin запроса — откуда
  бы они ни пришли (опции запроса, `headers` инстанса, interceptor), — а запрос,
  в котором остался хотя бы один портальный заголовок, отправляется с
  `redirect: 'error'`: cross-origin редирект same-origin эндпоинта не унесёт
  заголовки на адрес редиректа. Пользовательская опция `redirect` уважается
  только когда портальных заголовков в запросе нет. Явная отправка этих
  заголовков на чужой origin невозможна — это осознанное ограничение.
- **CSRF-токен передаётся только в заголовке** (никогда в URL или теле); свежий токен
  из ответа принимается только при same-origin URL ответа.
- **Ассеты action-ответа — только same-origin.** Конвейер ассетов (`X-Process-Assets`)
  запускается только для same-origin URL ответа; cross-origin URL ассета отбрасывается
  с ошибкой в консоли. Inline-строки не исполняются: допускаются только инертные
  `<script type="extension/settings">` и серверные реестры
  `BX.setJSList`/`BX.setCSSList`, аргумент которых разбирается строго как данные
  (`JSON.parse`, массив строк) — код из ответа не выполняется никогда.
- **Ограничение same-origin проверки ассетов.** Инвариант проверяет URL из ответа:
  HTTP-редирект same-origin URL на внешний адрес тегом `<script src>`/`<link href>`
  не перехватывается — браузер следует 30x сам (поведение идентично legacy `BX.load`).
  Open redirect на своём origin — отдельная уязвимость сервера, а не клиента.
- **Редиректы запроса с портальными заголовками запрещены** (`redirect: 'error'`):
  перенаправление Engine-эндпоинта (и любого same-origin запроса, несущего
  портальный заголовок) отклоняется, а не следуется (см. «Отличия поведения» ниже).

## Миграция с BX.ajax

| BX.ajax | HttpClient |
|---|---|
| `BX.ajax.runAction(name, {data})` | `HttpClient.action(name, {data})` |
| `BX.ajax.runAction(...).then(({data}) => ...)` | `const data = await HttpClient.action(...)` |
| доступ ко всему `{status, data, errors}` | `HttpClient.actionRaw(name, options)` |
| `BX.ajax.runAction(name, {json})` | `HttpClient.action(name, {json})` |
| `BX.ajax.runAction(name, {navigation: {page}})` | `HttpClient.action(name, {navigation: {page, size}})` |
| `BX.ajax.runAction(name, {analytics})` | `HttpClient.action(name, {analytics})` |
| `BX.ajax.runAction(name, {getParameters})` | `HttpClient.action(name, {query})` |
| обработка `response.errors` в `catch` | `catch (error)` → `error instanceof ControllerError`, `error.errors` |
| `response.data.html` от `Component`/`HtmlContent` | `const { html } = await HttpClient.action(...)` |
| `BX.ajax({url, method, dataType})` | `new HttpClient()` + `client.request({url, method, responseType})` |
| `BX.ajax.get(url)` / `BX.ajax.post(url, data)` | `HttpClient.get(url)` / `HttpClient.post(url, data)` |
| `xhr.abort()` | `AbortController` + опция `signal` |
| `BX.ajax({lsId})` (сериализация между вкладками) | опция `crossTabLockKey` — только очередь, без кеша |
| `lsTimeout` (срок жизни записи в localStorage, секунды) | `crossTabLockTimeout` — страховочный срок ожидания, миллисекунды; не время жизни кеша |
| `lsForce: true` (обойти сериализацию и кеш) | прямого соответствия нет: обход — это отсутствие `crossTabLockKey` в вызове |
| `BX.ajax.processRequestData` (разбор тела ответа) | `client.interceptors.response` |
| события `onAjaxSuccess` / `onParseJSONFailure` | `client.interceptors.response` (`onFulfilled` / `onRejected`) |
| правка запроса до отправки | `client.interceptors.request` |

Отличия поведения: результат `action()` — сразу `data` (не весь ответ);
любая неуспешность — reject типизированной ошибкой (не смесь resolve/reject как
в legacy); CSRF-повтор выполняется ровно один раз и только на same-origin.
Action-путь запрещает переходы по редиректу (`redirect: 'error'`): перенаправление
Engine-эндпоинта на внешний URL отклоняется `NetworkError`, а не следуется, — так
портальные заголовки не уходят на адрес редиректа. Сырой транспорт редиректы
по-прежнему следует, кроме запроса, в котором остался портальный заголовок, —
такой запрос тоже отправляется с `redirect: 'error'`.

Отдельно о `lsId`: устаревший механизм не только выстраивал запросы вкладок в
очередь, но и **кешировал тело ответа** — клал его в localStorage под ключом
`ajax-<lsId>` на `lsTimeout` секунд, и следующий вызов в пределах этого срока
получал сохранённое тело, не обращаясь к серверу. `crossTabLockKey` кеша не даёт:
он только сериализует одновременные вызовы и ничего не хранит, а вызов, пришедший
после того, как ведущая вкладка завершилась, идёт в сеть сам. Код, который
опирался на кеш `lsId`, при переходе нужно дополнить собственным кешированием —
перехватчиком ответа или своим хранилищем.
